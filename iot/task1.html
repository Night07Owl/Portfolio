ESP32 Web Server & HTML LED Control

Deploying a lightweight embedded HTTP web server on an ESP32 microcontroller to serve an interactive graphical dashboard over local Wi-Fi and toggle hardware actuators in real time.

01

Objective, Problem Statement & Project Summary

// OBJECTIVE & SUMMARY

Objective

  • • To develop a basic IoT-based LED control system using the ESP32.
  • • To configure the ESP32 as a web server over a Wi-Fi network.
  • • To create a simple web-based interface for controlling the LED.
  • • To enable the user to turn the LED ON and OFF remotely through a web browser.

Problem Being Addressed

  • • Traditionally, an LED connected to a microcontroller is controlled using a physical switch, push button, or predefined program logic.
  • • This project demonstrates a more convenient method of controlling the LED remotely through a web browser.
  • • It eliminates the need for a physical button and allows the LED to be controlled over a Wi-Fi network.

Project Summary

  • • The ESP32 is connected to a Wi-Fi network and configured to function as a local web server.
  • • The ESP32 hosts a simple web interface containing ON and OFF control buttons.
  • • When the user enters the ESP32's IP address in a browser, the control webpage is displayed.
  • • Selecting ON or OFF sends an HTTP request to the ESP32.
  • • The ESP32 receives the request and changes the LED state accordingly.
  • • This provides a simple example of wireless device control using an ESP32 web server.
02

Concepts (In My Own Words)

// FORGE RULE #1: OWN WORDS > COPY-PASTE

Embedded Web Server

Unlike hosting a website on a massive cloud server, an embedded web server runs directly inside the microcontroller's low-power dual-core processor. It listens for incoming TCP packets on port 80, parses HTTP request headers, and constructs an HTML payload on the fly to send back across the socket.

Client-Server Communication

The browser acts as the client and the ESP32 acts as the host server. Communication relies on the stateless HTTP request-response cycle over the local Wi-Fi TCP/IP stack. When the user taps a button, an HTTP GET request travels to the ESP32's local IP address, which inspects the URL path and modifies physical hardware.

GPIO Digital Switching

The microcontroller uses General Purpose Input/Output (GPIO) pins configured in output mode. Calling digitalWrite(pin, HIGH) drives 3.3V to the pin, providing current through a current-limiting resistor to illuminate the LED, while LOW grounds the circuit (0V).

The data flow is synchronous: The browser requests http://192.168.1.45/H. The ESP32 parses the line GET /H, executes digitalWrite(LED_PIN, HIGH), formats the HTTP 200 OK header, transmits the refreshed HTML page showing "LED is ON", and terminates the client socket to release memory.

Why the 220Ω Resistor is Critical:

The ESP32 pin delivers 3.3V. The LED forward drop is ~2.0V. By Ohm's law ($I = \frac{V_{pin} - V_f}{R}$): $I = \frac{3.3V - 2.0V}{220\Omega} \approx 5.9\text{ mA}$. This is safe for both the LED and the ESP32 pin (which has a maximum rated source current of 12mA).

Implementation & Source Code

// ARDUINO C++ FIRMWARE
ESP32_WebServer_LED_Control.ino 
#include <WiFi.h>

const char* ssid     = "YOUR_WIFI_SSID";
const char* password = "YOUR_WIFI_PASSWORD";

WiFiServer server(80);
const int ledPin = 2; // Onboard LED / External GPIO 2

void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW);

  Serial.print("Connecting to Wi-Fi");
  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  
  Serial.println("\nWi-Fi Connected!");
  Serial.print("ESP32 Web Server IP: http://");
  Serial.println(WiFi.localIP());

  server.begin();
}

void loop() {
  WiFiClient client = server.available();
  if (client) {
    String currentLine = "";
    while (client.connected()) {
      if (client.available()) {
        char c = client.read();
        if (c == '\n') {
          if (currentLine.length() == 0) {
            // Send standard HTTP 200 response header
            client.println("HTTP/1.1 200 OK");
            client.println("Content-type:text/html");
            client.println("Connection: close");
            client.println();
            
            // Serve Web Interface HTML
            client.println("<!DOCTYPE html><html><head>");
            client.println("<meta name='viewport' content='width=device-width, initial-scale=1'>");
            client.println("<style>body{font-family:sans-serif;text-align:center;background:#111;color:#fff;padding:40px;}");
            client.println(".btn{display:inline-block;padding:15px 30px;font-size:18px;margin:10px;border-radius:8px;text-decoration:none;color:#fff;}");
            client.println(".on{background:#00ff88;color:#000;}.off{background:#ff4757;}</style></head>");
            client.println("<body><h1>ESP32 LED Control</h1>");
            client.println("<p><a href='/H' class='btn on'>TURN ON</a></p>");
            client.println("<p><a href='/L' class='btn off'>TURN OFF</a></p>");
            client.println("</body></html>");
            break;
          } else {
            currentLine = "";
          }
        } else if (c != '\r') {
          currentLine += c;
        }

        // Parse HTTP request routes
        if (currentLine.endsWith("GET /H")) {
          digitalWrite(ledPin, HIGH);
        }
        if (currentLine.endsWith("GET /L")) {
          digitalWrite(ledPin, LOW);
        }
      }
    }
    client.stop();
  }
}

Challenges & Solutions Encountered

// FORGE RULE #2: SHOW THE FAILURE, NOT JUST FIX
FAILURE #1
Brownout Detector Triggered Repeatedly on Boot
Root Cause Analysis

When WiFi.begin() engaged the onboard RF radio transceiver, current draw surged instantaneously to ~240mA. The cheap USB development cable experienced excessive voltage drop below 2.7V, causing the ESP32 hardware Brownout Detector to reboot the chip in an endless boot loop.

Solution Implemented

Replaced the generic thin cable with a short, 24 AWG data-rated cable connected to a powered USB 3.0 port, and soldered a 100µF electrolytic decoupling capacitor across the 3V3 and GND power rails to absorb transient current spikes.

FAILURE #2
Web Server Unresponsive After Multiple Page Refreshes
Root Cause Analysis

Browsers request /favicon.ico immediately after loading a page. The request parsing loop did not gracefully close socket streams when unexpected paths occurred, exhausting the ESP32's free TCP client sockets (max 4 concurrent connections).

Solution Implemented

Added a timeout watchdog counter to the client.connected() while-loop and explicitly called client.stop() immediately after flushing the HTTP payload, freeing up RAM and socket descriptors.
