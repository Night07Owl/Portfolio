01

Overview

// OBJECTIVE & SUMMARY

The objective of this assignment is to implement autonomous cloud-level automation, eliminating the need for manual user interaction by reacting to external cloud events.

True IoT systems operate autonomously rather than acting solely as remote control switches. In this project, we integrated IFTTT (If This Then That) with Adafruit IO to construct an event-driven automation engine. When a trigger condition fires (such as a sunset schedule, a weather alert, or a custom Webhook HTTP POST event), IFTTT automatically executes an action that updates our Adafruit IO feed. The ESP32, which continuously listens to the feed via MQTT, detects the cloud value change and instantly toggles hardware relays and LEDs without any human intervention.

Concepts (In My Own Words)

// FORGE RULE #1: OWN WORDS > COPY-PASTE

What is IoT Automation?

Automation means replacing human manual intervention with deterministic programmatic rules. In an automated IoT architecture, sensors or cloud services act as event detectors, business logic evaluates criteria, and physical devices automatically adjust states in the real world.

The IFTTT Orchestrator

IFTTT ("If This Then That") is a cloud connector that translates events across hundreds of incompatible platforms. Instead of writing custom API integration code for every third-party service, IFTTT links an event from Service A directly into an input on Service B.

The Trigger → Action Paradigm

The architecture follows two steps:
Trigger ("If This"): An external condition occurs (e.g. time reaches 18:00 or Webhook event receives { "event": "motion" }).
Action ("Then That"): The output executed by the rule (writing "ON" to our Adafruit IO feed).

Implementation & Source Code

// ESP32 AUTOMATION FIRMWARE
ESP32_IFTTT_Adafruit_Automation.ino 
#include <WiFi.h>
#include "Adafruit_MQTT.h"
#include "Adafruit_MQTT_Client.h"

#define WIFI_SSID   "YOUR_WIFI_SSID"
#define WIFI_PASS   "YOUR_WIFI_PASSWORD"
#define AIO_SERVER  "io.adafruit.com"
#define AIO_USER    "YOUR_AIO_USERNAME"
#define AIO_KEY     "YOUR_AIO_KEY"

const int relayPin = 4;

WiFiClient client;
Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, 1883, AIO_USER, AIO_KEY);
Adafruit_MQTT_Subscribe autoFeed = Adafruit_MQTT_Subscribe(&mqtt, AIO_USER "/feeds/automation-feed");

void setup() {
  Serial.begin(115200);
  pinMode(relayPin, OUTPUT);
  digitalWrite(relayPin, LOW);

  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("\nWi-Fi Connected!");
  mqtt.subscribe(&autoFeed);
}

void loop() {
  if (!mqtt.connected()) {
    int8_t ret;
    while ((ret = mqtt.connect()) != 0) {
      mqtt.disconnect();
      delay(5000);
    }
  }

  Adafruit_MQTT_Subscribe *subscription;
  while ((subscription = mqtt.readSubscription(5000))) {
    if (subscription == &autoFeed) {
      String payload = String((char *)autoFeed.lastread);
      Serial.print("Automated Action Received: ");
      Serial.println(payload);

      if (payload.equalsIgnoreCase("ACTIVATE") || payload == "1") {
        digitalWrite(relayPin, HIGH);
        Serial.println("Hardware RELAY: ENGAGED");
      } else {
        digitalWrite(relayPin, LOW);
        Serial.println("Hardware RELAY: DISENGAGED");
      }
    }
  }

  if (!mqtt.ping()) {
    mqtt.disconnect();
  }
}

09

Challenges & Solutions Encountered

// FORGE RULE #2: SHOW THE FAILURE, NOT JUST FIX
FAILURE #1
Unpredictable Polling Latencies Exceeding 45 Seconds
Root Cause Analysis

When initially configured with an RSSI / Email trigger, IFTTT free tier only polls external providers every 15 to 60 minutes, which made real-time hardware actuation appear broken.

Solution Implemented

Replaced polling triggers with IFTTT Webhooks. Webhook endpoints trigger immediate synchronous push actions into Adafruit IO, dropping round-trip latency to under 1.2 seconds.

FAILURE #2
Duplicate Trigger Executions (Double Switching)
Root Cause Analysis

HTTP retries from the webhook source caused the applet to fire twice in rapid succession (within 200ms), causing relay chatter.

Solution Implemented

Implemented software debouncing on the ESP32: Any incoming command received within 3000ms of the previous state transition is ignored via a timestamp lock (millis() - lastTriggerTime > 3000).
