01

Overview

// OBJECTIVE & SUMMARY

The objective of this assignment is to develop an enterprise-style full-stack IoT telemetry application integrating edge sensor acquisition, secure cloud database synchronization, user authentication, and interactive web visualization.

We interfaced a DHT11 temperature & humidity sensor and an LDR (Light Dependent Resistor) with an ESP32 microcontroller, streaming calibrated physical readings to a Google Firebase Realtime Database. On the frontend, we developed a secure web application protected by Firebase Authentication (Email/Password). Authenticated users access a dynamic dashboard featuring live gauge dials for temperature and humidity, ambient lux metrics, and bidirectional toggle controls for an AC light bulb / relay. All state transitions sync across WebSockets in milliseconds without manual browser reloads.

Concepts (In My Own Words)

// FORGE RULE #1: OWN WORDS > COPY-PASTE

Cloud Service Models: IaaS, PaaS, SaaS & BaaS

IaaS (Infrastructure): Renting raw virtual machines and storage (e.g. AWS EC2).
PaaS (Platform): Deploying code where the cloud handles the OS (e.g. Heroku, App Engine).
SaaS (Software): Ready-to-use software products (e.g. Gmail, Google Docs).
BaaS (Backend as a Service): Pre-built backend services like databases, authentication, and file storage on demand (e.g. Firebase).

Firebase Realtime Database vs SQL

Unlike relational SQL databases structured in rows and tables, Firebase Realtime Database is a single NoSQL JSON tree. Instead of clients constantly sending HTTP GET requests to check for new data, Firebase keeps an open WebSocket connection, automatically "pushing" updates to clients whenever any node in the JSON tree changes.

Authentication vs Authorization

Authentication (Who are you?): Verifying identity via credentials (e.g. user enters email and password into Firebase Auth).
Authorization (What are you allowed to do?): Permission rules dictating whether that authenticated user can read or write to specific database paths (e.g. Firebase Database Security Rules: ".write": "auth != null").

Transducers: DHT11 & LDR

The DHT11 uses a capacitive humidity sensor and a thermistor with a dedicated internal IC to transmit digital serial pulses. The LDR is a cadmium-sulfide photoresistor whose electrical resistance decreases exponentially as ambient light increases, measured via an analog voltage divider circuit.

Wiring / Circuit Setup

// PIN CONNECTIONS
Device Pin ESP32 Pin Connection Type Notes
DHT11 Data Pin GPIO 4 (D4) Digital Input / Output Pulled up to 3.3V with 10kΩ resistor
DHT11 VCC / GND 3V3 / GND Power Supply Rail Regulated 3.3V power
LDR Divider Midpoint GPIO 34 (A2) Analog Input (ADC1) ADC1 pin (safe to read with Wi-Fi active)
Relay Signal IN GPIO 18 (D18) Digital Output Logic HIGH activates relay coil

Critical ESP32 Design Note — ADC1 vs ADC2:

The ESP32 has two ADC units: ADC1 (GPIOs 32–39) and ADC2 (GPIOs 0, 2, 4, 12–15, 25–27). ADC2 cannot be used when Wi-Fi is enabled because the Wi-Fi driver claims the peripheral. Connecting the LDR to ADC1 pin (GPIO 34) guarantees stable analog readings during wireless database transmissions.

Implementation & Source Code

// ESP32 FIRMWARE & WEB DASHBOARD
ESP32_Firebase_IoT.ino 
#include <WiFi.h>
#include <FirebaseESP32.h>
#include <DHT.h>

#define WIFI_SSID     "YOUR_WIFI_SSID"
#define WIFI_PASS     "YOUR_WIFI_PASSWORD"
#define FIREBASE_HOST "YOUR_PROJECT.firebaseio.com"
#define FIREBASE_AUTH "YOUR_DATABASE_SECRET"

#define DHTPIN 4
#define DHTTYPE DHT11
#define LDRPIN 34
#define RELAYPIN 18

DHT dht(DHTPIN, DHTTYPE);
FirebaseData fbdo;
FirebaseAuth auth;
FirebaseConfig config;

unsigned long lastSensorRead = 0;

void setup() {
  Serial.begin(115200);
  pinMode(RELAYPIN, OUTPUT);
  digitalWrite(RELAYPIN, LOW);
  dht.begin();

  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("\nWi-Fi Connected!");

  config.host = FIREBASE_HOST;
  config.signer.tokens.legacy_token = FIREBASE_AUTH;
  Firebase.begin(&config, &auth);
  Firebase.reconnectWiFi(true);
}

void loop() {
  // Sample sensors every 2500ms
  if (millis() - lastSensorRead > 2500) {
    lastSensorRead = millis();

    float t = dht.readTemperature();
    float h = dht.readHumidity();
    int ldrValue = analogRead(LDRPIN);

    if (!isnan(t) && !isnan(h)) {
      Firebase.setFloat(fbdo, "/iot_system/sensor_data/temperature", t);
      Firebase.setFloat(fbdo, "/iot_system/sensor_data/humidity", h);
      Firebase.setInt(fbdo, "/iot_system/sensor_data/light_level", ldrValue);
      Serial.printf("Updated Firebase -> Temp: %.1f C, Hum: %.1f %%, Light: %d\n", t, h, ldrValue);
    }
  }

  // Check for bulb state from web dashboard
  if (Firebase.getBool(fbdo, "/iot_system/controls/bulb_state")) {
    bool bulbState = fbdo.boolData();
    digitalWrite(RELAYPIN, bulbState ? HIGH : LOW);
  }
}

Challenges & Solutions Encountered

// FORGE RULE #2: SHOW THE FAILURE, NOT JUST FIX
FAILURE #1
DHT11 Returning NaN (Not A Number) Values
Root Cause Analysis

The DHT11 utilizes a single-wire proprietary protocol requiring at least 1000–2000ms between consecutive hardware reads. Reading the sensor inside a rapid loop (every 100ms) interrupted its capacitive measurement cycle.

Solution Implemented

Introduced a strict 2500ms timing constraint using millis() timer checks before calling dht.readTemperature(), guaranteeing accurate and non-corrupted floating-point values.

FAILURE #2
LDR Analog Reading Fluctuating on Wi-Fi Broadcasts
Root Cause Analysis

The LDR was initially wired to GPIO 25 (ADC2 channel). When Wi-Fi began transmission, the radio peripheral locked the ADC2 SAR controller, causing analog readings to jump erratically to 4095.

Solution Implemented

Re-routed the LDR voltage divider to GPIO 34 (ADC1 Channel 6), which is completely isolated from the Wi-Fi RF baseband processor and immune to RF noise.
