01

What I Built & Why

// OBJECTIVE & MOTIVATION

When I first started this project, I wanted to answer a simple question: Can a microcontroller that costs just a few dollars run its own independent web server and let me control physical hardware straight from my phone without any internet access?

In this task, I programmed an ESP32 DevKit V1 to connect to my local Wi-Fi network and host an embedded HTTP server on port 80. When I open the ESP32's assigned local IP address in any browser, the board serves a custom web interface with ON and OFF buttons. Tapping those buttons sends HTTP requests directly to the ESP32, which immediately sets GPIO 2 to HIGH (3.3V) or LOW (0V), toggling the LED in real time.

This is the foundation of smart hardware. Products like Philips Hue bulbs, smart plugs, and local gateway hubs all start with this exact principle of embedded network control.

02

Core Concepts (In Plain English)

// HOW THE TECHNOLOGY ACTUALLY WORKS

How Does an Embedded Server Work?

Instead of running on a massive data center server, the web server code runs directly inside the ESP32's microchip. It listens on port 80. When your phone asks for a page, the ESP32 literally constructs the HTML and CSS strings in its RAM and sends them back packet by packet over Wi-Fi.

HTTP: The Request & Response Rule

HTTP is strictly a "speak when spoken to" protocol. Your phone (the client) sends an HTTP GET request (like GET /H). The ESP32 (the server) receives that request, reads the URL path, changes the GPIO pin state, and sends back a response. The ESP32 cannot push data to the phone on its own unless the phone asks first.

Why Local Control Matters

Because everything happens inside the local Wi-Fi router (LAN), this system doesn't need an internet connection or any cloud service to function. If the outside internet goes down, local control still works with almost zero delay (< 150ms).

Implementation Source Code

// ARDUINO C++ FIRMWARE

Here is the complete Arduino sketch I wrote and flashed to the ESP32. Notice how concise and readable it is: We connect to Wi-Fi, start listening on port 80, and when a client requests /H or /L, we change the pin output and send back a clean HTML response.

ESP32_WebServer_LED_Control.ino 
#include <WiFi.h>

// Wi-Fi credentials
const char* ssid     = "YOUR_WIFI_SSID";
const char* password = "YOUR_WIFI_PASSWORD";

// Start server on port 80 (standard HTTP port)
WiFiServer server(80);
const int ledPin = 2;

void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW); // Start with LED OFF

  // Connect to local Wi-Fi network
  Serial.print("Connecting to ");
  Serial.println(ssid);
  WiFi.begin(ssid, password);

  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }

  Serial.println("
WiFi Connected!");
  Serial.print("Server IP Address: http://");
  Serial.println(WiFi.localIP());

  server.begin();
}

void loop() {
  WiFiClient client = server.available(); // Listen for incoming requests
  if (client) {
    String currentLine = "";
    while (client.connected()) {
      if (client.available()) {
        char c = client.read();
        if (c == '
') {
          if (currentLine.length() == 0) {
            // HTTP headers
            client.println("HTTP/1.1 200 OK");
            client.println("Content-type:text/html");
            client.println("Connection: close");
            client.println();
            
            // Responsive HTML Dashboard
            client.println("<!DOCTYPE html><html><head>");
            client.println("<meta name='viewport' content='width=device-width, initial-scale=1'>");
            client.println("<style>body{font-family:sans-serif;text-align:center;background:#131521;color:#fff;padding:40px;}");
            client.println(".btn{display:inline-block;padding:14px 28px;margin:10px;font-size:18px;border-radius:30px;text-decoration:none;font-weight:bold;}");
            client.println(".on{background:#E5857B;color:#fff;} .off{background:#45496A;color:#fff;}</style></head>");
            client.println("<body><h1>ESP32 Hardware Controller</h1>");
            client.println("<p>Toggle GPIO 2 Actuator:</p>");
            client.println("<a class='btn on' href='/H'>TURN ON</a>");
            client.println("<a class='btn off' href='/L'>TURN OFF</a>");
            client.println("</body></html>");
            client.println();
            break;
          } else {
            currentLine = "";
          }
        } else if (c != '
') {
          currentLine += c;
        }

        // Parse route
        if (currentLine.endsWith("GET /H")) { digitalWrite(ledPin, HIGH); }
        if (currentLine.endsWith("GET /L")) { digitalWrite(ledPin, LOW); }
      }
    }
    client.stop();
  }
}

Things That Broke & How I Solved Them

// HONEST ENGINEERING REFLECTION
FAILURE #1
The "Brownout Detector" Boot Loop Nightmare
What Went Wrong

As soon as the ESP32 tried to connect to Wi-Fi, it crashed and rebooted endlessly with the error message Brownout detector was triggered. I thought the board was broken.

How I Fixed It

It turned out the cheap, thin micro-USB cable I was using couldn't deliver the sudden ~250mA current spike that the Wi-Fi RF radio demands when starting up. The voltage dropped below 2.7V. I replaced it with a short, high-grade 24 AWG data cable plugged into a powered USB port, and added a 100µF capacitor across 3V3 and GND. It booted instantly.

FAILURE #2
Server Froze After a Few Page Refreshes (Socket Exhaustion)
What Went Wrong

The web page worked twice, but after refreshing a few times, the page stopped loading completely. The ESP32 didn't crash, but it stopped answering any HTTP requests.

How I Fixed It

Modern mobile browsers automatically send a second background request for /favicon.ico. Because my initial code didn't handle that route and didn't close the client connection, the ESP32's tiny 4-socket limit was quickly filled with hanging connections. I added an explicit client.stop() call at the end of every request cycle, completely eliminating the freeze.

The Problem: Going Global & Real-Time

// OBJECTIVE & MOTIVATION

From any laptop or smartphone anywhere on Earth, I can flip a virtual switch on my Adafruit IO dashboard, and within a fraction of a second, the command reaches my ESP32 and safely energizes an electromechanical relay module that switches a 230V AC light bulb.

02

HTTP vs MQTT: Why MQTT Wins for IoT

// PUB/SUB ARCHITECTURE EXPLAINED

The Restaurant vs The Radio Station

HTTP is like a restaurant waiter: you have to ask every single time you want water. If you want updates, you have to keep asking. MQTT is like tuning a radio to a frequency: you subscribe once to a topic (like /feeds/bulb-state), and the moment the station broadcasts a song, your radio plays it with zero asking.

Lightweight Packets (< 2 Bytes Header)

An HTTP request carries hundreds of bytes of bulky text headers (user agents, cookies, caching tags). An MQTT packet header can be as tiny as 2 bytes! This tiny footprint makes MQTT drastically faster and allows the ESP32 to maintain persistent low-power connections.

Galvanic Isolation (Safe 230V Switching)

Microcontrollers run on 3.3V DC; wall sockets carry lethal 230V AC. A relay module acts as a physical bridge: a low-voltage electromagnet pulls an isolated metal contact shut. The 3.3V brain and the 230V mains never touch electrically.

Implementation Source Code

// ADAFRUIT MQTT SUBSCRIBER FIRMWARE
ESP32_AdafruitIO_MQTT_Relay.ino 
#include <WiFi.h>
#include "Adafruit_MQTT.h"
#include "Adafruit_MQTT_Client.h"

#define WLAN_SSID       "YOUR_WIFI_SSID"
#define WLAN_PASS       "YOUR_WIFI_PASSWORD"
#define AIO_SERVER      "io.adafruit.com"
#define AIO_SERVERPORT  1883
#define AIO_USERNAME    "YOUR_AIO_USERNAME"
#define AIO_KEY         "YOUR_AIO_ACTIVE_KEY"

const int relayPin = 26;
WiFiClient client;
Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, AIO_SERVERPORT, AIO_USERNAME, AIO_KEY);

// Subscribe to feed
Adafruit_MQTT_Subscribe lightControl = Adafruit_MQTT_Subscribe(&mqtt, AIO_USERNAME "/feeds/led-control");

void MQTT_connect();

void setup() {
  Serial.begin(115200);
  pinMode(relayPin, OUTPUT);
  digitalWrite(relayPin, LOW); // Active-HIGH default OFF

  WiFi.begin(WLAN_SSID, WLAN_PASS);
  while (WiFi.status() != WL_CONNECTED) { delay(500); }

  mqtt.subscribe(&lightControl);
}

void loop() {
  MQTT_connect();

  Adafruit_MQTT_Subscribe *subscription;
  while ((subscription = mqtt.readSubscription(5000))) {
    if (subscription == &lightControl) {
      char* val = (char*)lightControl.lastread;
      if (strcmp(val, "1") == 0 || strcmp(val, "ON") == 0) {
        digitalWrite(relayPin, HIGH);
      } else {
        digitalWrite(relayPin, LOW);
      }
    }
  }
}

void MQTT_connect() {
  int8_t ret;
  if (mqtt.connected()) { return; }
  while ((ret = mqtt.connect()) != 0) {
    mqtt.disconnect();
    delay(5000);
  }
}

Things That Broke & How I Solved Them

// HONEST ENGINEERING REFLECTION
FAILURE #1
Active-LOW Relay Logic Inversion (Light Turned ON when Told OFF)
What Went Wrong

When I clicked "TURN ON" in Adafruit IO, the relay clicked OFF. When I clicked "TURN OFF", the bulb turned ON! It was completely inverted.

How I Fixed It

Many hobby relay modules feature an optocoupler with Active-LOW logic: bringing the control pin LOW sinks current and energizes the coil. I resolved this in firmware by either inverting the GPIO write or connecting the light bulb to the NC (Normally Closed) terminal depending on desired default safety states.

FAILURE #2
MQTT Disconnected Every 60 Seconds (Keepalive Failure)
What Went Wrong

The ESP32 connected cleanly to Adafruit IO, but after exactly one minute, the broker disconnected the board with an error.

How I Fixed It

The MQTT specification requires client pings to prove the connection is alive. Because I had a blocking delay(10000) in my loop, the ESP32 was missing its ping window. I refactored the loop to use non-blocking millis() and added an automatic reconnection watchdog.

What I Built & Why

// OBJECTIVE & MOTIVATION

Manual switches are great, but true home automation means things should happen automatically when specific conditions occur in the real world or in the cloud.

In Task 3, I connected IFTTT ("If This Then That") as an event orchestrator between web services, email alerts, and my ESP32 hardware. The moment the event triggers, the ESP32 acts immediately, and I receive an email confirmation verifying the event.

02

The Trigger → Action Paradigm

// EVENT-DRIVEN LOGIC

What is an Event-Driven Architecture?

Traditional programs run in a continuous loop asking "did anything change yet?". Event-driven systems sleep until an external event (like a webhook POST) triggers a notification, allowing systems to respond immediately without wasting CPU cycles.

IFTTT as the Universal Translator

IFTTT connects hundreds of incompatible ecosystems (Google Assistant, iOS shortcuts, Maker Webhooks, Adafruit IO, and Gmail). It takes an input from Service A and transforms it into the exact API payload needed by Service B.

Synchronous Webhooks vs Slow Polling

Polling means checking periodically (which on free cloud tiers can take up to 15-45 minutes). Webhooks are instant HTTP POST callbacks sent immediately when the event happens, dropping latency to under 1.2 seconds.

        digitalWrite(relayPin, HIGH);
      } else {
        digitalWrite(relayPin, LOW);
      }
    }
  }
}

How Firebase Realtime Database Works

// CLOUD CONCEPTS EXPLAINED

What is BaaS (Backend as a Service)?

Instead of managing Linux servers, installing PostgreSQL, and setting up SSL certificates, Firebase provides a complete turnkey backend in the cloud with built-in authentication, database syncing, and security rules.

The Live JSON Tree

Firebase Realtime Database isn't a traditional table with rows and columns. It is a single giant JSON document. When the ESP32 updates /iot_system/sensor_data/temperature, Firebase pushes just that tiny changed key over WebSockets to every connected phone in milliseconds.

Digital vs Analog Transducers

The DHT11 uses a single-wire digital protocol with an internal thermistor and capacitive humidity sensor. The LDR is an analog resistor whose resistance drops in light; we measure it using the ESP32's 12-bit Analog-to-Digital Converter (ADC) yielding values from 0 to 4095.

// ESP32 FIREBASE TELEMETRY FIRMWARE
ESP32_Firebase_IoT.ino 
#include <WiFi.h>
#include <FirebaseESP32.h>
#include <DHT.h>

#define WIFI_SSID     "YOUR_WIFI_SSID"
#define WIFI_PASS     "YOUR_WIFI_PASSWORD"
#define FIREBASE_HOST "YOUR_PROJECT.firebaseio.com"
#define FIREBASE_AUTH "YOUR_DATABASE_SECRET"

DHT dht(4, DHT11);
FirebaseData fbdo;
FirebaseAuth auth;
FirebaseConfig config;

void setup() {
  Serial.begin(115200);
  pinMode(18, OUTPUT);
  dht.begin();

  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) { delay(500); }

  config.host = FIREBASE_HOST;
  config.signer.tokens.legacy_token = FIREBASE_AUTH;
  Firebase.begin(&config, &auth);
  Firebase.reconnectWiFi(true);
}

void loop() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  int ldr = analogRead(34); // Safe on ADC1

  if (!isnan(t) && !isnan(h)) {
    Firebase.setFloat(fbdo, "/iot_system/sensor_data/temperature", t);
    Firebase.setFloat(fbdo, "/iot_system/sensor_data/humidity", h);
    Firebase.setInt(fbdo, "/iot_system/sensor_data/light_level", ldr);
  }

  // Check for bulb toggle commands from frontend
  if (Firebase.getBool(fbdo, "/iot_system/controls/bulb_state")) {
    digitalWrite(18, fbdo.boolData() ? HIGH : LOW);
  }
  delay(2500); // Push every 2.5 seconds
}

Things That Broke & How I Solved Them

// HONEST ENGINEERING REFLECTION
FAILURE #1
The Infamous ADC2 Wi-Fi Conflict (LDR Reading Always 0 or 4095)
What Went Wrong

Initially, my LDR read light levels perfectly on the Serial Monitor. But the moment the Wi-Fi connected to push data to Firebase, analogRead() started returning garbage (either 0 or 4095). I was bewildered.

How I Fixed It

After digging through the ESP32 silicon errata datasheet, I uncovered a critical hardware fact: The ESP32 has two separate ADCs. ADC2 is shared with the Wi-Fi radio circuitry. When Wi-Fi transmits, ADC2 pins (GPIO 0, 2, 4, 12-15, 25-27) are blocked by the Wi-Fi driver! I immediately re-wired the LDR to GPIO 34 (which belongs to ADC1). ADC1 operates completely independently from the Wi-Fi radio, and the readings became crystal clear.

02

Closed-Loop Automation & Hysteresis

// WHY HYSTERESIS SAVES HARDWARE

What is Relay Chatter?

If you program a simple rule like "turn light ON if light < 1500", what happens at sunset when light fluctuates between 1499 and 1501? The relay will click on and off 50 times a second! This is called relay chatter, and it will quickly destroy the mechanical relay contacts or burn out the bulb.

The Hysteresis Deadband Solution

We solve chatter by introducing a dual-threshold deadband: the light turns ON only when darkness drops below 1400 ADC, but does NOT turn off until room light climbs past 1700 ADC. The 300-point difference prevents flickering from shadows or slight clouds.

Time-Series vs Overwriting Records

Instead of updating a single node, we append each measurement to a chronological list with a timestamp. This creates an audit log of indoor climate history that can be graphed and analyzed over weeks.

Implementation Source Code

// CAPSTONE AUTOMATION FIRMWARE
ESP32_Capstone_Automation_Logging.ino 
#include <WiFi.h>
#include <FirebaseESP32.h>
#include <DHT.h>

const int THRESHOLD_DARK  = 1400;
const int THRESHOLD_LIGHT = 1700;

DHT dht(4, DHT11);
FirebaseData fbdo;
bool currentBulbState = false;
String currentMode = "AUTOMATIC";

void loop() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  int ldr = analogRead(34);

  // Check user mode selection from dashboard
  if (Firebase.getString(fbdo, "/iot_system/config/mode")) {
    currentMode = fbdo.stringData();
  }

  if (currentMode == "AUTOMATIC") {
    // Autonomous Hysteresis Logic
    if (ldr < THRESHOLD_DARK && !currentBulbState) {
      currentBulbState = true;
      digitalWrite(18, HIGH);
      Firebase.setBool(fbdo, "/iot_system/system_state/bulb_state", true);
    } else if (ldr > THRESHOLD_LIGHT && currentBulbState) {
      currentBulbState = false;
      digitalWrite(18, LOW);
      Firebase.setBool(fbdo, "/iot_system/system_state/bulb_state", false);
    }
  } else {
    // Manual Mode: Listen directly to user toggle button
    if (Firebase.getBool(fbdo, "/iot_system/controls/manual_bulb")) {
      currentBulbState = fbdo.boolData();
      digitalWrite(18, currentBulbState ? HIGH : LOW);
    }
  }

  // Log snapshot to time-series tree
  String path = "/iot_system/logs/" + String(millis() / 1000);
  FirebaseJson json;
  json.set("temperature", t);
  json.set("humidity", h);
  json.set("light", ldr);
  json.set("bulb_state", currentBulbState);
  json.set("mode", currentMode);
  Firebase.set(fbdo, path, json);

  delay(2500);
}
