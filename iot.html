ESP32 Web Server & HTML LED Control

Deploying a lightweight embedded HTTP server on an ESP32 microcontroller to serve an interactive dashboard over local Wi-Fi and toggle hardware actuators with zero internet dependence.

01

Overview

// OBJECTIVE & SUMMARY

The objective of this assignment is to bridge embedded hardware with browser-based interfaces by configuring an ESP32 microcontroller as a standalone local HTTP web server.

Traditional microcontrollers require physical tethering via UART serial monitors or physical display shields for control. Here, we solve that friction by connecting the ESP32 to a local 2.4 GHz Wi-Fi network in Station (STA) mode, binding an HTTP server on port 80, and serving a responsive HTML5 user interface directly from flash memory. When a client on the same local subnet visits the ESP32's assigned DHCP IP address, clicking buttons dispatches HTTP GET requests (such as /H and /L) that directly modulate the digital logic state of GPIO pin 2, toggling a high-brightness LED with zero cloud reliance.

02

Concepts (In My Own Words)

// FORGE RULE #1: OWN WORDS > COPY-PASTE

Embedded Web Server

Unlike hosting a website on a massive cloud server, an embedded web server runs directly inside the microcontroller's low-power dual-core processor. It listens for incoming TCP packets on port 80, parses HTTP request headers, and constructs an HTML payload on the fly to send back across the socket.

Client-Server Communication

The browser acts as the client and the ESP32 acts as the host server. Communication relies on the stateless HTTP request-response cycle over the local Wi-Fi TCP/IP stack. When the user taps a button, an HTTP GET request travels to the ESP32's local IP address, which inspects the URL path and modifies physical hardware.

GPIO Digital Switching

The microcontroller uses General Purpose Input/Output (GPIO) pins configured in output mode. Calling digitalWrite(pin, HIGH) drives 3.3V to the pin, providing current through a current-limiting resistor to illuminate the LED, while LOW grounds the circuit (0V).

Implementation Source Code

// ARDUINO C++ FIRMWARE
ESP32_WebServer_LED_Control.ino 
#include <WiFi.h>

const char* ssid     = "YOUR_WIFI_SSID";
const char* password = "YOUR_WIFI_PASSWORD";

WiFiServer server(80);
const int ledPin = 2;

void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW);

  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) { delay(500); }
  
  Serial.print("ESP32 Web Server IP: http://");
  Serial.println(WiFi.localIP());
  server.begin();
}

void loop() {
  WiFiClient client = server.available();
  if (client) {
    String currentLine = "";
    while (client.connected()) {
      if (client.available()) {
        char c = client.read();
        if (c == '\n') {
          if (currentLine.length() == 0) {
            client.println("HTTP/1.1 200 OK\nContent-type:text/html\nConnection: close\n");
            client.println("<h1>ESP32 LED Control</h1><a href='/H'>TURN ON</a> | <a href='/L'>TURN OFF</a>");
            break;
          } else { currentLine = ""; }
        } else if (c != '\r') { currentLine += c; }

        if (currentLine.endsWith("GET /H")) { digitalWrite(ledPin, HIGH); }
        if (currentLine.endsWith("GET /L")) { digitalWrite(ledPin, LOW); }
      }
    }
    client.stop();
  }
}

Challenges & Solutions Encountered

// FORGE RULE #2: SHOW FAILURE, NOT JUST FIX
FAILURE #1
Brownout Detector Triggered Repeatedly on Boot
Root Cause Analysis

When the RF radio initialized, current draw spiked to ~240mA. The thin USB cable experienced voltage drop below 2.7V, causing the chip to reboot endlessly.

Solution Implemented

Switched to a 24 AWG data-rated cable on a powered USB 3.0 port and soldered a 100µF decoupling capacitor across 3V3 and GND rails.

FAILURE #2
Web Server Unresponsive After Multiple Page Refreshes
Root Cause Analysis

Browser requests for /favicon.ico did not close sockets properly, exhausting the ESP32's free TCP client sockets (max 4 concurrent connections).

Solution Implemented

Added a watchdog timeout to the client connection loop and explicitly called client.stop() immediately after flushing the HTTP payload.

02

Concepts (In My Own Words)

// FORGE RULE #1: OWN WORDS > COPY-PASTE

What is MQTT?

MQTT is an ultra-compact messaging protocol created specifically for battery-powered microcontrollers and unreliable wireless links. Unlike bulky HTTP with large text headers, MQTT packets can be as tiny as 2 bytes, keeping network traffic and power consumption near zero.

Publisher, Broker & Subscriber

Instead of direct peer-to-peer connections, MQTT uses a central post office called the Broker (Adafruit IO). A Publisher sends a message to a topic. The Subscriber (ESP32) listens to that topic. The publisher and subscriber never know each other's IP address.

Feeds & Topics

Topics act like specific channels or inbox addresses. In Adafruit IO, topics are organized hierarchically as username/feeds/feed-name. Devices subscribe to this exact path to receive real-time updates.

Implementation Source Code

// ESP32 MQTT FIRMWARE
ESP32_AdafruitIO_MQTT.ino 
#include <WiFi.h>
#include "Adafruit_MQTT.h"
#include "Adafruit_MQTT_Client.h"

#define WLAN_SSID       "YOUR_WIFI_SSID"
#define WLAN_PASS       "YOUR_WIFI_PASSWORD"
#define AIO_SERVER      "io.adafruit.com"
#define AIO_USERNAME    "YOUR_AIO_USERNAME"
#define AIO_KEY         "YOUR_AIO_KEY"

const int ledPin = 2;
WiFiClient client;
Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, 1883, AIO_USERNAME, AIO_KEY);
Adafruit_MQTT_Subscribe ledFeed = Adafruit_MQTT_Subscribe(&mqtt, AIO_USERNAME "/feeds/led-control");

void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  WiFi.begin(WLAN_SSID, WLAN_PASS);
  while (WiFi.status() != WL_CONNECTED) { delay(500); }
  mqtt.subscribe(&ledFeed);
}

void loop() {
  if (!mqtt.connected()) {
    int8_t ret;
    while ((ret = mqtt.connect()) != 0) {
      mqtt.disconnect();
      delay(5000);
    }
  }

  Adafruit_MQTT_Subscribe *subscription;
  while ((subscription = mqtt.readSubscription(5000))) {
    if (subscription == &ledFeed) {
      String payload = String((char *)ledFeed.lastread);
      if (payload == "ON" || payload == "1") { digitalWrite(ledPin, HIGH); }
      if (payload == "OFF" || payload == "0") { digitalWrite(ledPin, LOW); }
    }
  }

  if (!mqtt.ping()) { mqtt.disconnect(); }
}

FAILURE #1
Frequent Disconnections with Error Code -4 (Connection Lost)
Root Cause Analysis

A blocking delay(2000) prevented the client library from dispatching background keep-alive ping packets in time, causing the cloud broker to disconnect.

Solution Implemented

Replaced blocking delays with non-blocking millis() timer loops, ensuring mqtt.ping() is called periodically with an automatic reconnect helper.

Root Cause Analysis

ESP32 was publishing on every single loop pass (~100 times/second), exceeding the free limit of 30 data points per minute.

Solution Implemented

Implemented state-change detection: the ESP32 only publishes when currentState != previousState, ensuring zero wasted packets.

02

Concepts (In My Own Words)

// FORGE RULE #1: OWN WORDS > COPY-PASTE

What is IoT Automation?

Automation means replacing human manual intervention with deterministic programmatic rules. In an automated IoT architecture, sensors or cloud services act as event detectors, business logic evaluates criteria, and physical devices automatically adjust states in the real world.

The IFTTT Orchestrator

IFTTT ("If This Then That") is a cloud connector that translates events across hundreds of incompatible platforms. Instead of writing custom API integration code for every third-party service, IFTTT links an event from Service A directly into an input on Service B.

Trigger → Action Paradigm

Trigger ("If This"): An external condition occurs (e.g. Webhook event receives { "event": "motion" }). Action ("Then That"): The output executed by the rule (writing "ACTIVATE" to our Adafruit IO feed).

// ESP32 FIRMWARE
ESP32_Firebase_IoT.ino 
#include <WiFi.h>
#include <FirebaseESP32.h>
#include <DHT.h>

#define WIFI_SSID     "YOUR_WIFI_SSID"
#define WIFI_PASS     "YOUR_WIFI_PASSWORD"
#define FIREBASE_HOST "YOUR_PROJECT.firebaseio.com"
#define FIREBASE_AUTH "YOUR_DATABASE_SECRET"

DHT dht(4, DHT11);
FirebaseData fbdo;
FirebaseAuth auth;
FirebaseConfig config;

void setup() {
  Serial.begin(115200);
  pinMode(18, OUTPUT);
  dht.begin();
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) { delay(500); }

  config.host = FIREBASE_HOST;
  config.signer.tokens.legacy_token = FIREBASE_AUTH;
  Firebase.begin(&config, &auth);
}

void loop() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  int ldr = analogRead(34);

  if (!isnan(t) && !isnan(h)) {
    Firebase.setFloat(fbdo, "/iot_system/sensor_data/temperature", t);
    Firebase.setFloat(fbdo, "/iot_system/sensor_data/humidity", h);
    Firebase.setInt(fbdo, "/iot_system/sensor_data/light_level", ldr);
  }

  if (Firebase.getBool(fbdo, "/iot_system/controls/bulb_state")) {
    digitalWrite(18, fbdo.boolData() ? HIGH : LOW);
  }
  delay(2500);
}

Concepts (In My Own Words)

// FORGE RULE #1: OWN WORDS > COPY-PASTE

Closed-Loop Automation & Hysteresis

In a closed-loop system, sensor feedback automatically drives actuator outputs. To prevent relay chatter (rapid flickering when readings hover around a single point), we implement a hysteresis band: the light turns ON below 1400 raw ADC, but requires the room to brighten beyond 1700 raw ADC before switching OFF.

Time-Series Database Logging

Instead of constantly overwriting a single node, time-series logging records every reading as an immutable, timestamped event under a chronological log tree (e.g. /logs/2026-10-08/1728362400). This enables historical trend analysis and auditing.

Client-Side Data Export (Blob & CSV)

Modern browsers can serialize JSON records into RFC 4180 Comma Separated Values (CSV), bundle the string into an in-memory Blob object, and trigger a native file download using a temporary anchor element.

Hysteresis Calibration & Thresholds

// SENSOR TUNING

Dual-Point Hysteresis Deadband Logic:

1. Full Ambient Light (Daylight): Raw ADC reading ~3200–3500.
2. Dusk / Room Shadow: Raw ADC reading ~1500–1600.
3. Darkness (Night / Hand Covered): Raw ADC reading < 1000.
4. Software Rules: Turn ON when Light < 1400; Turn OFF when Light > 1700. The 300-point buffer zone eliminates false switching from passing shadows.

Implementation Source Code

// CAPSTONE AUTOMATION FIRMWARE
ESP32_Capstone_Automation_Logging.ino 
#include <WiFi.h>
#include <FirebaseESP32.h>
#include <DHT.h>

const int THRESHOLD_DARK  = 1400;
const int THRESHOLD_LIGHT = 1700;

DHT dht(4, DHT11);
FirebaseData fbdo;
bool currentBulbState = false;
String currentMode = "AUTOMATIC";

void loop() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  int ldr = analogRead(34);

  if (currentMode == "AUTOMATIC") {
    if (ldr < THRESHOLD_DARK && !currentBulbState) {
      currentBulbState = true;
      digitalWrite(18, HIGH);
      Firebase.setBool(fbdo, "/iot_system/system_state/bulb_state", true);
    } else if (ldr > THRESHOLD_LIGHT && currentBulbState) {
      currentBulbState = false;
      digitalWrite(18, LOW);
      Firebase.setBool(fbdo, "/iot_system/system_state/bulb_state", false);
    }

FAILURE #1
Relay Rapid Oscillations (Chatter) Around Single Threshold
Root Cause Analysis

When room light hovered right at 1500, subtle shadows caused the ADC reading to bounce above and below 1500 multiple times a second, switching the relay noisily.

Solution Implemented

Programmed dual asymmetric hysteresis limits: ON at < 1400 ADC, OFF at > 1700 ADC, eliminating false toggles.
